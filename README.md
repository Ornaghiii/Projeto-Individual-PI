# Football Database — Sistema de Cadastro de Jogadores

Projeto Individual da disciplina de Programação Web, com integração entre um front-end em **HTML/CSS/JavaScript Vanilla** e uma API REST em **Java + Spring Boot + JdbcTemplate**, persistindo os dados em banco relacional **H2**.

A aplicação permite cadastrar, listar, editar e remover jogadores de futebol, associando cada jogador a um time carregado dinamicamente a partir da API.

## Tecnologias utilizadas

- **Back-end:** Java 21, Spring Boot, Spring Web (MVC), Spring JDBC (`JdbcTemplate`), H2 Database (em memória)
- **Front-end:** HTML5, CSS3 e JavaScript puro (sem frameworks ou bibliotecas), consumindo a API via `fetch()`
- **Build:** Maven (`pom.xml`)

## Como executar o projeto

### Pré-requisitos

- JDK 21
- Maven (ou usar o wrapper `mvnw` incluso no projeto)
- Extensão **Live Server** (VS Code) ou qualquer servidor estático, para rodar o front-end

### 1. Executando o back-end

```bash
cd backend/jogadores
./mvnw spring-boot:run
```

A API sobe em `http://localhost:8080`.

Ao iniciar, o Spring Boot cria automaticamente as tabelas `jogador` e `times` a partir do arquivo `src/main/resources/schema.sql` e popula a tabela `times` com um conjunto inicial de times.

> **Observação:** o H2 roda em memória (`jdbc:h2:mem:meu_banco`), portanto os dados são reiniciados a cada vez que a aplicação é reiniciada. O console do H2 fica disponível em `http://localhost:8080/h2-console`.

### 2. Executando o front-end

1. Abra a pasta `frontend/` no VS Code.
2. Clique com o botão direito em `index.html` e selecione **Open with Live Server** (o front-end normalmente sobe em `http://127.0.0.1:5500`).
3. Com o back-end já rodando na porta `8080`, o front-end passa a consumir a API automaticamente ao carregar a página (o dropdown de times e a lista de jogadores são carregados via `fetch()`).

### Comunicação entre front-end e back-end

O cliente (`frontend/index.html`) faz requisições `fetch()` diretamente para `http://localhost:8080`. O back-end libera essas requisições através da anotação `@CrossOrigin(origins = "http://127.0.0.1:5500")` presente nos controllers, permitindo a comunicação entre as duas origens diferentes (Live Server × Spring Boot).

## Modelo de dados

```sql
CREATE TABLE jogador (
    id INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    numero INT NOT NULL,
    dtNasc DATE NOT NULL,
    sexo VARCHAR(20) NOT NULL,
    time VARCHAR(100) NOT NULL,
    posicao VARCHAR(50) NOT NULL,
    pe VARCHAR(20) NOT NULL,
    caracteristicas VARCHAR(500)
);

CREATE TABLE times (
    id INT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nome VARCHAR(100) NOT NULL
);
```

A tabela `times` já vem pré-populada com alguns clubes brasileiros e é a fonte de dados do `<select>` de times no formulário de cadastro.

## Endpoints da API

Base URL: `http://localhost:8080`

### Jogadores (`/jogadores`)

| Método | Endpoint         | Descrição                          | Status de sucesso |
|--------|------------------|-------------------------------------|--------------------|
| GET    | `/jogadores`     | Lista todos os jogadores cadastrados| 200 OK             |
| POST   | `/jogadores`     | Cadastra um novo jogador             | 201 Created        |
| PUT    | `/jogadores/{id}`| Atualiza os dados de um jogador     | 200 OK / 404 Not Found |
| DELETE | `/jogadores/{id}`| Remove um jogador                   | 204 No Content / 404 Not Found |

#### GET `/jogadores`

Resposta (200 OK):

```json
[
  {
    "id": 1,
    "nome": "Yuri Alberto",
    "numero": 9,
    "dtNasc": "2001-08-18",
    "sexo": "masculino",
    "time": "Corinthians",
    "posicao": "Atacante",
    "pe": "Direito",
    "caracteristicas": "Velocidade,Finalização"
  }
]
```

#### POST `/jogadores`

Requisição:

```json
{
  "nome": "Yuri Alberto",
  "numero": 9,
  "dtNasc": "2001-08-18",
  "sexo": "masculino",
  "time": "Corinthians",
  "posicao": "Atacante",
  "pe": "Direito",
  "caracteristicas": "Velocidade,Finalização"
}
```

Resposta (201 Created): o mesmo objeto enviado, confirmando o cadastro.

#### PUT `/jogadores/{id}`

Requisição: mesmo formato do POST, com os campos atualizados.

Respostas:
- `200 OK` com o objeto atualizado, se o jogador existir.
- `404 Not Found`, se o `id` informado não existir na base.

#### DELETE `/jogadores/{id}`

Respostas:
- `204 No Content`, se o jogador foi removido com sucesso.
- `404 Not Found`, se o `id` informado não existir na base.

### Times (`/times`)

| Método | Endpoint  | Descrição                                             | Status de sucesso |
|--------|-----------|----------------------------------------------------------|--------------------|
| GET    | `/times`  | Lista os times cadastrados (usado para popular o `<select>`)| 200 OK             |

## Validações

- **Front-end:** antes de enviar a requisição de cadastro/edição, o JavaScript verifica se todos os campos obrigatórios foram preenchidos (nome, número, data de nascimento, sexo, time, posição, pé dominante e ao menos uma característica), exibindo uma mensagem de erro e interrompendo o envio caso algum esteja ausente.
- **Back-end:** os endpoints `PUT` e `DELETE` verificam a existência do jogador no banco antes de executar a operação, retornando `404 Not Found` quando o `id` não existe. Isso garante que a API não confie apenas na validação feita pelo cliente.

## Restrições do projeto atendidas

- Front-end desenvolvido exclusivamente em HTML5, CSS3 e JavaScript Vanilla, sem frameworks ou bibliotecas externas.
- Back-end em Java/Spring Boot utilizando apenas as dependências iniciais do projeto (Web, JDBC, H2).
- Persistência via `JdbcTemplate` em banco relacional (H2).
- Uso de `fetch()` para todas as chamadas à API.
- Dropdown de times carregado dinamicamente via `GET /times`, sem valores fixos no HTML.
